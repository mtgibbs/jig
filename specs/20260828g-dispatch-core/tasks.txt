T1: extract the transport-agnostic dispatch core in scripts/dispatch/dispatcher.py. Define a new module-level function `dispatch(intent, event_id, *, ledger_path, image, namespace)` that takes an ALREADY-PARSED intent mapping — never a chat string — and performs the whole sequence in order: if the event id is already in the ledger, return without launching anything; otherwise render the Job, launch it, record the event id, and return the same result mapping `handle_event` returns today. Then rewrite `handle_event(text, event_id, *, ledger_path, image, namespace)` so that its entire body is: parse the intent from the text; if there is none, return the no-intent result; otherwise return the result of calling `dispatch`. After this change `handle_event` must NOT itself call the Job renderer, the launcher, the ledger reader or the ledger writer — it calls the parser and it calls `dispatch`, and nothing else. There must be exactly one copy of the dedupe-render-launch-record sequence in the module, because that sequence is the idempotency mechanism and two copies of it will drift. The externally visible behaviour of `handle_event` must not change at all: same arguments, same result keys, same ordering guarantees. Do not add an optional text parameter to `dispatch` — that would preserve the weld under a new name and let a future transport slip a chat string through.

T2: add the run registry to scripts/dispatch/dispatcher.py. Define `record_run(registry_path, record)` which appends one run record, and `read_runs(registry_path)` which returns the records as a list of mappings, plus `get_run(registry_path, event_id)` returning the single record with that event id or None. Store the records as one JSON object per line so a partially written file costs at most the last record. A record holds exactly these six fields and no others: the event id, the repo, the spec, the strategy, the Job name, and a coarse status string. A missing registry file is NOT an error — `read_runs` returns an empty list and `record_run` creates the file and any missing parent directory. All three functions must tolerate an unreadable or unwritable path without raising, and `read_runs` must skip a corrupt line rather than failing the whole read: the registry is descriptive, and a dispatcher that crashes because its index is damaged is worse than one that reports less. Keep this store SEPARATE from the event ledger — do not read or write the ledger path in these functions and do not store the registry inside the ledger file. The ledger answers one question and is the correctness mechanism for dedupe; if dedupe depended on this richer structure, a corrupt registry would silently break idempotency.

T3: record every launched run in the registry, from inside `dispatch` in scripts/dispatch/dispatcher.py. Thread the same new keyword argument through `handle_event` so the chat path records runs too. A run that is skipped because the event id was already seen must NOT produce a second record — the registry says what was launched, and a replayed event launches nothing. When no registry path is supplied the dispatcher must still work and simply not record, so that an existing caller does not break. Change nothing about the ledger, the renderer or the launcher in this task.

T4: add the second transport adapter, `launch_run(repo, spec, strategy, event_id, *, ledger_path, image, namespace, registry_path=None)`, to scripts/dispatch/dispatcher.py. It takes the repo, spec and strategy as SEPARATE VALUES, builds the intent mapping directly from them, and returns the result of calling `dispatch`. It must NOT call the chat parser and must NOT build a chat string to feed through it — an internal API whose behaviour depends on chat grammar is exactly the defect this spec exists to remove. It must not re-implement dedupe, rendering or launching: an adapter may build an intent and may format a result, and may not decide anything. If the strategy argument is empty or None, fall back to the same default the chat parser uses, taken from the same module-level constant rather than a second literal. This function is what an HTTP `launch_run` handler and an MCP tool will call, and its existence is what proves the seam is real — a seam with one caller has not been shown to be a seam.
