T1: create scripts/dispatch/api.py with the server skeleton, its configuration and its authentication. Build on the standard library's http.server and nothing else — no third-party web framework. Define a request handler class and a module-level function named exactly `serve(port)` which binds that port and serves requests. Read all configuration from the environment at startup: the shared bearer token from `HARNESS_API_TOKEN`; the event ledger path from `HARNESS_LEDGER_PATH`; the run registry path from `HARNESS_REGISTRY_PATH`; the worker image from `HARNESS_WORKER_IMAGE`; and the namespace from `HARNESS_NAMESPACE`, defaulting to the literal `harness-fleet`. If `HARNESS_API_TOKEN` is unset or empty, `serve` MUST refuse to bind and must exit the process non-zero with a message naming that variable. Do not fall back to running without authentication and do not merely warn: an endpoint that creates compute must have no default-open mode, because that mode is what runs in production the day the secret fails to mount. Every request must present that token in an `Authorization: Bearer <token>` header; a request without it, or with the wrong one, gets HTTP 401 and reaches no dispatcher function at all. All responses carry a JSON body. Import the dispatcher module and call its functions — do not copy any of its logic into this file.

T2: add the run-creation route to scripts/dispatch/api.py. A `POST` to the path `/runs` reads a JSON body carrying `repo`, `spec` and optionally `strategy`, and starts a run by calling the dispatcher's `launch_run` function with those values as separate arguments. It must NOT build a chat string and must NOT call the chat parser: an internal API whose behaviour depends on chat grammar is the defect the previous spec removed. A request missing `repo` or `spec` gets HTTP 400 and starts nothing. The body may also carry an idempotency key; when present, that key is used as the event id, so sending the same request twice starts exactly one run and the second response reports the existing run rather than a new one. When the key is absent the server mints a unique event id itself. Do NOT derive the key from the request contents such as by hashing repo and spec — two deliberate runs of the same spec are the normal case after a fix, and content-derived keys would silently collapse the second one. Respond with the run's identity and a success status code. This handler parses a request and formats a response; it must not call the Job renderer, the launcher or either ledger function directly.

T3: add the two read routes to scripts/dispatch/api.py. A `GET` to `/runs` returns the list of run records by calling the dispatcher's `read_runs`, as a JSON array under a named key rather than a bare top-level array. A `GET` to `/runs/<id>` returns the single record for that event id by calling the dispatcher's `get_run`, or HTTP 404 with a JSON body when no such run exists. Neither route may read the registry file directly, re-parse it, or filter the full list in this file when the dispatcher already offers the lookup — the handler's job is to call one dispatcher function and format the result. Neither route creates anything.

T4: add the cancel route to scripts/dispatch/api.py. A `DELETE` to `/runs/<id>` cancels the run by deleting its Kubernetes Job. Look the run up first: when no such run exists, return HTTP 404 and run no command. Otherwise delete the Job named in that run's record, in the dispatcher's namespace, by running the same external command the dispatcher uses to apply — read the command name from the environment variable `HARNESS_KUBECTL`, defaulting to the literal `kubectl`, so that a test can substitute a mock and assert on the arguments. Report whether the deletion succeeded in the JSON response. Do not raise when the command is missing.

T5: add the evidence route to scripts/dispatch/api.py. A `GET` to `/runs/<id>/evidence` must return HTTP 501 with a JSON body explaining that a run's evidence is written to a path that is not committed and does not survive the pod, so the capability does not exist yet. Return 501 rather than 404: a 404 would mean there is no such run, while the truth is that the run may exist and the system cannot serve its evidence. The route exists so that the gap stays visible instead of being forgotten. Do not attempt to read any evidence directory.

T6: write docs/dispatch-api.md and update scripts/dispatch/README.md. The document must describe every route — method, path, what the request carries, what the response carries, and which status codes it can return — precisely enough that a separate MCP server could be written against the document without reading the server source, because that MCP server is a client of this API and must never reimplement its logic. State that authentication is a bearer token from the environment and that the server refuses to start without one. Explain the idempotency key: what it is for, what happens when it is supplied twice, what happens when it is omitted, and why it is not derived from the request contents. Say plainly that the evidence route returns 501 by design and what would have to change for it to work. In README.md, add a short section pointing at the new document and stating that the HTTP API is one more adapter over the same shared core, not a second copy of it.
