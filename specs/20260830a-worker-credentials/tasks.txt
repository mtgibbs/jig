T1: add worker_secret() to scripts/dispatch/dispatcher.py and render the envFrom it resolves. Same shape as worker_image() and resolved at the same point, in dispatch(), from the same intent: HARNESS_WORKER_SECRET_<STRATEGY_UPPER_SNAKE> when set, else HARNESS_WORKER_SECRET, else nothing. Reuse worker_image()'s upper-snake derivation exactly — re.sub(r"[^A-Za-z0-9]", "_", strategy).upper() — because two maps that resolve per-strategy config differently are two things to reason about and the second is always the one somebody forgets. When it resolves, the rendered Job's container carries exactly one new field, envFrom: [{"secretRef": {"name": <resolved>}}]. When it resolves to nothing the key must be ABSENT, not empty and not None: an envFrom of [] is a different object from no envFrom, and "an unconfigured dispatcher renders what it renders today" is a claim about the rendered dict rather than about intent. Resolve it in dispatch() beside the image and for the same reason the image is resolved there — the strategy naming the Job's STRATEGY env, the strategy selecting its image and the strategy selecting its secret must be the SAME value read once, because a build-codex run on the codex image carrying the LiteLLM strategy's secret is the failure this task exists to make impossible and all three halves read as correct in isolation. A per-strategy variable set for one strategy must never be used for another: fall back to the shared default or to nothing, never to a sibling. Change nothing else about render_job — not the env list, not the nodeSelector, not the bounds, not the pod spec — and do not add serviceAccountName, because a pull secret on the namespace's default ServiceAccount already covers image pulls without the Job body naming anything. No credential VALUE may appear anywhere: this resolves the NAME of a secret and nothing more.

T2: document the worker credential contract in docs/executors.md. The contract is a set of VARIABLE NAMES, not a mechanism — exec-opencode.sh acquires nothing and takes provider configuration from the environment — so name the variables a worker expects and then give the three contexts that supply them: a laptop where they are already exported (oc reads Keychain or 1Password), a local container via docker run -e or --env-file, and a k8s Job via envFrom a Secret. Say plainly that a local run needs no Kubernetes concept at all, because envFrom is simply not rendered when nothing is configured; that is the portability property this whole design is arranged around and a reader who misses it will assume the fleet is a prerequisite. Then record the three identities and what each may do: the dispatch API token creates compute, the clone credential reads the repo a worker was handed, and the OUTCOME PAT pushes a branch and opens a PR and may never launch compute. Explain why the last two are separate rather than one PAT doing both: a worker that only ever needed to read is otherwise holding the credential that can write, and the worker is the least-trusted component in the system because it runs a model that writes code into a tree and then executes that repository's own verify.sh. Note that per-strategy secrets mean a build-codex worker never holds the LiteLLM key. Do not document the manifests — namespace, RBAC, quota and the node label are pi-cluster's and get their own spec there. Change no executable behaviour in this task.
