T1: make the resume predicate's gate bound generous, overridable and announced, in `_task_satisfied` in `scripts/ralph-build.sh`. Replace the hardcoded `timeout 60` with a bound read from `RALPH_SATISFIED_TIMEOUT`, in seconds, defaulting to a value no smaller than the loop's own executor bound `RALPH_EXEC_TIMEOUT` — a gate is not permitted to be slower than the work it judges, and a predicate that cannot outwait its own gate has no purpose, which is the whole defect: the same gate runs UNBOUNDED in `run_gates` a few lines away, so the strict bound sits on the cheaper of the two questions. Treat an unset, empty or non-positive-integer value as absent and use the default, never zero — a bound of no time at all would disable resume everywhere while looking like configuration, exactly the failure `HARNESS_ARTIFACT_MAX_BYTES` is written to avoid. Keep the bound finite: a hanging gate must still fail closed rather than wedge the run, which is why the bound exists and that reason is still good. Then separate the two refusals, which today collapse into one silent `return 1` whose branches are identical: when the gate RAN and did not pass, announce that its gate did not pass; when the gate did not FINISH inside the bound, announce that, naming the bound and how to raise it. Both still return not-satisfied — this changes what a reader is told, never what the predicate decides. Announce on the same stream and in the same shape as the other task lines, naming the task, because a task that runs when it should have been skipped is otherwise indistinguishable from a task that was never skippable, and the difference is a bound to raise versus work still to do. Every other uncertain case stays exactly as it is and stays fail-closed: no `tasks/` directory, no gate for the task, a gate that cannot be run, `RALPH_FORCE_ALL`, and `RALPH_FORCE_FROM` at or below this task's index all continue to answer not-satisfied. Do not touch `run_gates`, the attempt loop, the no-op guard, or the skip path's existing announcement, and do not cache, record or read back any verdict — reading a recorded gate result instead of re-running one is a genuine option and belongs to its own spec.
