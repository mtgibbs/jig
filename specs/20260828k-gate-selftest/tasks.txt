T1: create scripts/gate-selftest.sh with its argument handling and its hermetic workspace, and nothing else. It takes one argument, the path to a task directory — the kind holding a `verify.sh` and a `mutants/` subdirectory. Refuse with a clear message and a non-zero exit when the argument is missing, when the directory does not exist, when it holds no `verify.sh`, or when it holds no `mutants/` directory; each of those is a different message naming what was wrong, because a tool that says only "usage" makes the caller guess which of four things it got wrong. Then build the workspace: copy the repository into a temp directory and do all subsequent work there. It must never write inside the repository it was pointed at — several specs in this repo assert that files outside their own scope are untouched, so a self-test that leaves a mutant behind fails an unrelated spec's gate and looks like someone else's bug. Remove the temp directory when the script exits, including on failure. In this task the script does nothing after building the workspace except exit zero; T2 parses mutants and T3 runs them. Write `return 0` explicitly at the end of any function whose last construct is a loop or a conditional: a function inherits the exit status of its last construct, and for a loop that is its terminating condition, which is reliably non-zero — this exact trap silently killed every run of the previous spec's implementation.

T2: add mutant parsing to scripts/gate-selftest.sh. Each file directly under the task directory's `mutants/` is a mutant: a complete replacement artifact whose leading comment lines carry three fields — `MUTANT:` naming the assertion id it must break, `TARGET:` giving the repository-relative path it replaces, and `WHY:` explaining the defect it introduces. Read all three from each file. A mutant missing `MUTANT:` or missing `TARGET:` is an ERROR that fails the run, naming the file — never a skip: a silently skipped mutant is an assertion nobody is checking, which is the precise state this tool exists to detect, so the tool must not be able to create it. `WHY:` is required to be present but its content is free text; carry it, because it is what a failure message needs in order to explain itself. Accept the fields in any order and allow other comment lines around them. Print nothing per mutant in this task and run nothing: T3 installs and runs them, T4 decides verdicts. Change no behaviour added in T1.

T3: add mutant installation and the bounded gate run to scripts/gate-selftest.sh. T4: add the verdict and the report to scripts/gate-selftest.sh. A mutant is KILLED only when BOTH of these hold: the gate exited non-zero, AND the gate's output contains a FAIL line naming that mutant's declared `MUTANT:` assertion id. Those are two separate requirements and both must be enforced. A mutant that made the gate fail for some OTHER reason is a third outcome, WRONG-REASON, and must not be counted as a kill — it proves nothing about the assertion it claims to cover, and accepting it leaves exactly the unfalsifiable assertion this tool exists to find. This is not hypothetical: while validating an earlier gate by hand, one mutant patched a code path the assertion never exercised and another modelled a bash trap belonging to a different construct; both looked like weak assertions and were mutants that missed. A mutant the gate ACCEPTED is a SURVIVOR and is this tool's headline failure — report it prominently, naming the mutant file, its declared id and its `WHY:` text, so the reader learns what the assertion failed to notice. A mutant that made the gate hang is reported as HUNG. Print one line per mutant and a final summary line counting each outcome. Exit non-zero if any mutant survived, was wrong-reason, or hung. Do not add the coverage check or the pend check here; T5 owns both.

T5: add the two static checks on the gate itself to scripts/gate-selftest.sh. First, coverage: collect every assertion id the task's `verify.sh` uses in its own `ok` and `no` calls, collect every id declared by a mutant, and fail the run naming any gate id that no mutant declares. An assertion no mutant exercises has never been observed to work, which is the same state as one that cannot fail — mutation testing detects a weak assertion, but only this check detects an unexercised one. Second, the `pend` ban: fail the run naming the file if the task's `verify.sh` INVOKES `pend` — a line where it appears as a command, such as at the start of a line or after `then`, `else`, `do`, `;`, `&&` or `||`. Ban the verb, not the word: a gate that merely mentions `pend` in a comment or in an assertion message must pass, and gates in this very spec do exactly that because they are the ones asserting the ban. A check that cannot tell a call from a mention would fail its own author's correct work, which is how `specs/lib/assert.sh` was nearly given an impossible instruction. A per-task gate asserts only its own task's criteria, so it has nothing to defer, and `specs/lib/assert.sh` deliberately does not define the verb. Fold both failures into the exit code the run already returns from T4. Add no new mutant handling and change no verdict logic.
