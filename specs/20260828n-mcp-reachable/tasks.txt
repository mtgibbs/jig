T1: write scripts/mcp-probe.sh, which answers whether one named MCP server is actually usable from where the loop is standing. It takes a server name and an optional config path, resolves that server's endpoint URL and the NAME of the environment variable its credential interpolates out of the config, and performs exactly one MCP `initialize` round trip against the endpoint. Print one line naming the outcome class and exit 0 only when the server answered `initialize` with a result carrying serverInfo. Distinguish the failures rather than collapsing them, because collapsing them is the bug this exists to prevent: `unconfigured` when the named server is not in the config or the variable it interpolates is unset or empty, and in that case make NO network call at all; `unreachable` when the name does not resolve or the connection is refused or the bound elapses; `unauthorized` when the endpoint answers 401 or 403; and `not-an-mcp-endpoint` when the endpoint answers but not with MCP, which specifically includes any HTML body and a 404 on an OAuth registration path. That last class is not hypothetical tidiness — an empty credential produced a 401, a client fell back to OAuth dynamic client registration, and the operator saw `Cannot POST /register` and spent an hour believing the cluster was down. Bound every call with a short timeout so a server that accepts a connection and never answers costs seconds rather than a run. Send only `initialize`; never call a tool, because a preflight with side effects is not a preflight. The credential's VALUE must never appear in output, in an error message, or in a process argument — only the variable's name may be printed. Use curl when it is available and python3 otherwise. Do not touch run-loop.sh in this task; T4 owns it.

T2: pass the MCP endpoint and credential into the container, in scripts/exec-container.sh and docker/loop-executor.Dockerfile. The container today receives HARNESS_LITELLM_KEY, OC_SHEET and the RALPH_* variables and nothing else, so a spec that declares an MCP server reaches task 1 inside a container that has no MCP at all. Add MCP_HOMELAB_API_KEY to the passthrough using exactly the discipline already established: passed through by NAME with the value taken from the loop's environment and never re-derived, and a variable that is unset in the loop must be UNSET in the container rather than set to the empty string — an empty credential is precisely what produced the misleading 404 that motivated this spec. Use the single name MCP_HOMELAB_API_KEY and no synonym; two names for one secret is the first of the three faults recorded in the spec. The container's endpoint is the in-cluster Service, http://mcp-homelab.mcp-homelab.svc.cluster.local:3000/mcp, because a Job talking to a Service in its own cluster has no reason to leave through the ingress, terminate TLS and resolve a public name to come back in; the ingress URL stays correct for a laptop and must not be removed. Do not mint any new credential — the key already exists in 1Password as mcp-homelab/api-key and reaches the cluster through the mcp-homelab-secrets ExternalSecret, and a second one would recreate the fault this spec is about. Change nothing about how the preflight decides anything; T4 owns that.

T3: document the MCP path in docs/loop-container.md. State the two endpoints and which is for which — the in-cluster Service URL that a Job uses and the ingress URL that a laptop uses — and say why the in-cluster one exists, that a Job has no reason to leave the cluster and come back through TLS and public DNS to reach a Service beside it. Name the single environment variable MCP_HOMELAB_API_KEY and say plainly that it is one name everywhere and that the alternative spelling is the fault that cost an hour on 2026-08-28. Record that the credential is reused rather than minted: it already exists as the 1Password item mcp-homelab/api-key delivered by the mcp-homelab-secrets ExternalSecret, and a loop Job mounts that same Secret. Document what the probe checks and, more importantly, what its four failure classes mean to a reader staring at one, especially that `not-an-mcp-endpoint` is what an HTML 404 from an OAuth registration path looks like and that it means a credential or endpoint problem rather than a server that is down. Say that a spec declaring no MCP, or declaring none, causes no probe and no network call and behaves exactly as it does today, and that this is guaranteed rather than incidental. Change nothing under scripts/ or docker/.

T4: make the preflight ask the server instead of the filesystem, in scripts/run-loop.sh. This task is LAST and must stay last, because bash reads a running script by byte offset and run-loop.sh is the script being run; a nonzero exit immediately after this task is expected rather than a failure, and the loop is re-invoked rather than resumed. The existing MCP block currently derives a config filename from the binding and checks that the file exists, which is a check that passes for a reason unrelated to what it claims — it cannot tell a working server from a broken one, a valid key from a rotated one, or a config naming the right server from one naming a server that was deleted. Keep the block's structure, keep the collected-misses idiom, and keep exit 3, which readers already key on as "the container needs attention, not another retry". Keep deriving the config PATH from RALPH_EXEC_CMD exactly as it does now, since the binding still decides which config is read; what changes is that the file's contents are used rather than its existence. For each declared server whose value is not `none`, run the probe from T1 and, when it fails, report both the server name and the class it returned, because a preflight that says only "MCP unavailable" hands the reader the same undifferentiated answer that made this necessary. A spec that declares no MCP field, or declares none, must produce no probe, no network call and not one byte of added output — run-loop.sh has to keep running on a laptop with no infrastructure, and that portability bar is not negotiable for a convenience.
