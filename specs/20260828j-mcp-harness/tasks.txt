T1: create scripts/mcp-harness/server.py with the JSON-RPC skeleton, its configuration and the initialize handshake. Use only the Python standard library — no third-party package is installed in this container and none may be added. The server speaks JSON-RPC 2.0 over stdin and stdout: read one JSON object per line from stdin, write one JSON object per line to stdout, and keep going until stdin closes. Read two settings from the environment at startup: the dispatcher's base URL from `HARNESS_API_URL` and the shared bearer token from `HARNESS_API_TOKEN`. If either is unset or empty, exit non-zero with a message naming the missing variable and serve nothing at all — the same fail-closed rule scripts/dispatch/api.py already follows, and for the same reason: a tool server that starts without knowing who it is will be started that way in production the day the secret fails to mount. Handle the `initialize` method by returning a JSON-RPC result carrying a protocol version and a server name identifying this as the harness server. A request whose JSON does not parse, or which names a method this server does not implement, gets a JSON-RPC error response and the server keeps running: a crash on one malformed frame denies the whole session to the caller. Define the request-handling entry point as a module-level function named exactly `main`, so a test can drive it. Do not import the `dispatcher` module anywhere in this file, now or in any later task: this server is a CLIENT of the HTTP API and must not carry a second copy of the launch machinery. Implement no tools in this task; T2 owns the catalogue and T3 onward own the individual tools.

T2: add the tool catalogue to scripts/mcp-harness/server.py — the answer to `tools/list`. Return exactly four tools and no others: `list_runs`, `run_status`, `fetch_evidence` and `launch_run`. Do NOT include `cancel_run`; it is deliberately deferred to its own spec because it is the tool a model reaches for while tidying up, it has no undo, and its blast radius grows with the size of the fleet. Each tool carries a name, a description and a JSON Schema for its arguments. Treat the description and the schema as the contract the calling MODEL reads, because that is what they are — they are prompt, not documentation. `list_runs` takes no arguments. `run_status` and `fetch_evidence` each take a required `run_id`. `launch_run` takes `repo`, `spec`, `strategy` and `idempotency_key`, and all four are REQUIRED with no default for any of them. Do not make `idempotency_key` optional and do not generate one when it is absent: an optional key defaulting to a fresh value is the exact bug docs/dispatch-api.md warns clients about, because every retry then arrives with a new key, the dispatcher's replay protection never engages, and a retried tool call silently becomes a second run. Say so in that parameter's description, and tell the caller to pass the id of the thing that caused the run — an issue number, a commit sha, an event id. Write each description to say what the tool does NOT do as well as what it does: `fetch_evidence` must say evidence does not leave the pod yet, and `launch_run` must say a replayed key returns the existing run rather than starting a second one. Do not implement `tools/call` for any tool in this task; T3 onward own the behaviour.

T3: add the HTTP transport and the two read tools to scripts/mcp-harness/server.py. Write one helper that performs a request against `HARNESS_API_URL` using `urllib.request`, sends the `Authorization: Bearer <token>` header on every call, and returns the status code and the decoded body without raising on an HTTP error status — a 404 is an answer, not an exception. Give that helper a bounded timeout so a hung dispatcher cannot wedge the MCP session forever. Then implement `tools/call` for `list_runs`, which GETs `/runs`, and `run_status`, which GETs `/runs/<run_id>`. Both are READ tools and must issue nothing but GET: a read tool that mutates is the failure this server's whole shape exists to prevent. Map the failure codes to distinct, actionable results rather than one generic error, because the caller is a model that will act on the words: a 401 says the request was not authenticated and must NOT claim the run does not exist; a 404 from `run_status` says there is no run with that id; any other non-success says the dispatcher rejected the request and quotes what it said. The value of `HARNESS_API_TOKEN` must never appear in any result, error or log line this file produces — not even truncated. Do not implement `fetch_evidence` or `launch_run` here; T4 and T5 own them.

T4: add the `fetch_evidence` tool to scripts/mcp-harness/server.py. It GETs `/runs/<run_id>/evidence`. That route answers **501** today and will keep answering 501 until evidence can leave the pod at all, which is ADR-001 decision D5 and is not built. Report that as its own distinct outcome: the tool result must say the capability is not implemented yet, and must be clearly different from the result `run_status` produces for an unknown run id. Do not flatten the two together and do not report 501 as a generic failure — a caller that cannot tell "there is no such run" from "this service cannot answer that yet" will go looking for a missing run that exists, which is the precise reason the API returns 501 rather than 404 in the first place. Where it helps the caller, name D5 as the reason the capability is absent, so the result explains itself rather than merely refusing. This tool is a read and must issue nothing but GET. Change no other tool.

T5: add the `launch_run` tool to scripts/mcp-harness/server.py — the only tool in this server that changes anything. It POSTs to `/runs` a JSON body carrying the four fields the caller supplied: `repo`, `spec`, `strategy` and `idempotency_key`. Send the caller's key through unchanged; never substitute, regenerate or fall back to a value of your own, and never retry the POST on your own initiative — a retry the server decided is a duplicate run the caller cannot see and did not ask for. A success returns the run the dispatcher reports. The dispatcher answers a replayed idempotency key with success and starts no second run, so report that outcome as an existing run rather than as an error or as a new launch — a caller told "failed" for a replay will retry, which is exactly the loop this design prevents. A 400 means the dispatcher found the request incomplete: say which field it named rather than reporting a bare status code. A 401 says authentication, and the token's value must not appear in the result. Change no other tool and add no second mutation.

T6: write docs/mcp-harness.md and point to it from README.md. Document all four tools with their arguments and what each returns, the two configuration variables `HARNESS_API_URL` and `HARNESS_API_TOKEN` and the fail-closed rule that the server refuses to start without them, and how the three failure codes differ — 401 authentication, 404 no such run, 501 a capability that does not exist yet — stating that a client must not collapse them. Explain that `idempotency_key` is required and must be the id of the thing that caused the run, and what goes wrong when a caller generates a fresh one per attempt. Record why `cancel_run` is absent, as a decision rather than an omission, and where it will land. State the boundary this server sits on: it is a CLIENT of the cluster-internal dispatch API, it holds no cluster credentials and needs no RBAC, and the cluster-administration tools in `mcp-homelab` are deliberately a separate server — a diagnostic agent should not silently gain the ability to start runs, and a fleet orchestrator should not inherit the ability to restart deployments. Do not change scripts/mcp-harness/server.py in this task: it is documentation only.
