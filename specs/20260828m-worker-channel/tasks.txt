T1: make the loop report its status outward, in scripts/ralph-status.sh. Read two settings from the environment: a base URL from `HARNESS_REPORT_URL` and a bearer token from `HARNESS_REPORT_TOKEN`. When the URL is unset or empty the loop must behave EXACTLY as it does today — write its file, post nothing, and print nothing about it — because `run-loop.sh` has to keep running on a laptop with no infrastructure, and that is the portability bar this whole design is built to clear. When the URL is set, every status the loop already writes is also POSTed as JSON to `{base}/runs/{run_key}/status`, where the run key is the identity the loop already has, `<host>/<agent>-<pid>`; do not mint a second identity, because two names for one run are two names that will disagree. Send the token as an `Authorization: Bearer` header when one is set. Use `curl` when it is available and `python3` otherwise. The POST is fire-and-forget and its own failure must be SILENT and total: an unreachable coordinator, a connection refused, a 500, a timeout — none of them may fail, stall or alter the run, and none may print anything that would be mistaken for a loop error. Bound every call with a short timeout, because a coordinator that accepts a connection and never answers must not hold a build. Add the POST to the existing `hb_write` rather than adding new reporting points; the record and the moments it is written at are already correct and must not change. The token's value must never appear in any output. Do not post attempt records in this task and do not poll for anything; T2 and T3 own those.

T2: post each attempt record as it is written, in scripts/ralph-log.sh. The per-attempt metadata record that `log_meta` already composes — outcome, duration, exec and verify status, byte counts — is POSTed as JSON to `{base}/runs/{run_key}/attempts` using the same configuration, the same fire-and-forget discipline, the same bound and the same silence on failure that T1 established for status. Reuse T1's helper rather than writing a second one: two posting paths would drift, and the second one is always the one that leaks the token or blocks. Post the record the writer already built; do not compose a different or reduced one, because the point is that what a reader sees matches what the evidence tree holds. As in T1, doing nothing at all when no URL is configured is the required behaviour and not a degraded mode. Do not touch the status posting from T1 and do not add polling.

T3: poll for a control intent and honour a cancel, in scripts/ralph-build.sh. Between attempts and between tasks — the two moments the loop is between units of work and can act without abandoning anything in flight — GET `{base}/runs/{run_key}/control` and read an action from the JSON answer. When the action is `cancel`, stop the run cleanly: stamp a terminal phase on the heartbeat so the run does not freeze mid-record claiming to be running, say plainly on stdout that it was cancelled, and exit non-zero with a status distinct from a gate failure, because a cancelled run is not a failed one and a reader must be able to tell them apart. Every other case means carry on: no URL configured, an unreachable coordinator, a timeout, a non-2xx answer, a body that does not parse, an action that is absent or unrecognised. Fail OPEN on the channel and CLOSED on the intent — a coordinator being down must never stop a build, and an answer that cannot be read must never be treated as a cancel. Bound the call. Do not implement pause here; T4 owns it.

T4: honour a pause intent, in scripts/ralph-build.sh. When the polled action is `pause`, the loop holds before starting the next unit of work instead of proceeding: it keeps writing its heartbeat so a reader can see it is alive, marks the phase as paused so a paused run is visibly paused rather than indistinguishable from a hung one, and re-polls on a sleep interval rather than spinning. It leaves the hold when the action becomes anything other than `pause` — carrying on when there is no action, and cancelling when the action is `cancel`, using the cancel behaviour T3 already built rather than a second copy of it. A paused loop must remain interruptible by the ordinary means and must not hold a lock or a temp resource that a human would have to clean up. Change nothing about how the intent is fetched; T3 owns the fetch, and this task owns only what the loop does when the answer is `pause`.

T5: document the channel in docs/. Explain the two environment variables and state plainly that with no URL configured the loop posts nothing, polls nothing and behaves exactly as before — that is the portability guarantee and a reader needs to know it is guaranteed rather than incidental. Document the three endpoints, the run key that identifies a run, and the JSON each direction carries. Record WHY the channel is outbound in both directions: nothing can connect into a worker, because a container has no published port and a k8s Job has an ephemeral name and then ceases to exist, so a control cannot be sent to a worker and must instead be noticed by it while polling — exactly how a GitHub Actions or GitLab runner discovers that its job was cancelled. Say that this is what makes the worker portable rather than what limits it. Document the failure discipline: fail open on the channel and closed on the intent, so a coordinator that is down never stops a build and an unreadable answer is never treated as a cancel. Note what deliberately is not here — the coordinator itself, transcript streaming, and any inbound endpoint — and where each belongs. Change nothing under `scripts/`.
